# ZMS CS Helper - 프로젝트 개발/코딩 지침 및 환경 가이드

본 문서는 프로젝트에 참여하는 모든 작업자 및 AI 에이전트가 반드시 준수해야 할 **기술 환경 및 코딩 규칙**입니다.

## 🎯 [대전제] 사내 협업 및 계정 간 다방향 소통 SaaS 지향점
본 서비스는 단순한 개인 비서가 아닌 **"사내 다중 상담원(Multi-Agent) 협업 및 공유 관제 플랫폼"**입니다. 다음 사항을 개발 및 설계 시 항상 최우선으로 인지하고 구현해야 합니다.

1. **상담사 개별 로그인 및 데이터 전체 공유**:
   - 각 상담사는 개별 계정으로 활동하며, 본인이 작성한 상담 내역은 DB를 통해 전체 상담사에게 즉시 공유되어야 합니다.
   - 유선 전화가 들어오거나 고객을 검색했을 때, **"이 고객이 과거에 어떤 상담 직원과 무슨 내용으로 상담을 나눴는지"** 즉각 검색 및 추적이 가능해야 합니다.
2. **상담(티켓)의 유기적인 담당자 변경 및 인수인계**:
   - 상담 건의 담당자를 타 상담사로 지정(배정)하거나, 내가 담당으로 가져오는 등 **업무 주체(담당자)가 실시간으로 달라지는 흐름**이 자연스럽게 지원되어야 합니다.
3. **계정 간 실시간 다방향 소통 및 동기화**:
   - 검색, 워크스페이스, 칸반보드, 캘린더 등 모든 관제 뷰는 한 상담원의 화면 내부 동기화를 넘어 **여러 상담원 계정 간에 실시간으로 데이터가 물 흐르듯 다방향 동기화**되도록 처리해야 합니다.

## 0-0. 🚨 [필수] 모든 AI 에이전트 세션 시작 시 1단계 의무 이행 수칙 (Mandatory Initialization)
**모든 AI 에이전트/모델은 사용자의 새로운 대화 세션이나 첫 요청을 받는 즉시 아래 3단계를 가장 먼저 수행해야 합니다.**

1. **가이드 문서 실시간 조회**: 프로젝트 루트의 `DEVELOPMENT_GUIDE.md`와 `PROJECT_ROADMAP.md`를 `view_file` 도구로 즉시 조회하여 최신 아키텍처 및 작업 현황을 파악합니다.
2. **타입스크립트 컴파일 상태 확인**: `npx tsc --noEmit` 명령을 실행하여 현재 기존 소스코드에 컴파일 에러가 없는지 먼저 점검합니다.
3. **중복 코드/폴더 생성 원천 차단**: 기존에 이미 만들어진 `src/front/`, `src/backend/` 및 커스텀 훅(`useAppData`, `useCtiCollector` 등)의 유틸리티와 컴포넌트를 우선 재활용하며 동일 기능의 레거시 중복 폴더(`src/components/`, `src/lib/services/` 등)를 생성하지 않습니다.

## 0. 🛠️ 기술 스택 및 환경 (Tech Stack & Environment)
작업 중 임의로 새로운 프레임워크나 백엔드 서버를 추가하는 것을 금지하며, 아래 지정된 스택 내에서만 개발합니다.

- **프론트엔드 (UI & Client)**
  - **환경**: React 18 + Vite + TypeScript
  - **스타일링**: Tailwind CSS + Lucide React (아이콘)
  - **특징**: 싱글 페이지 애플리케이션(SPA) 형태로 구동됨.
- **백엔드 (Database & Auth)**
  - **환경**: Supabase (PostgreSQL 기반 BaaS)
  - **특징**: 별도의 Node.js/Express 커스텀 서버 없이 프론트엔드에서 Supabase Client를 통해 DB를 직접 호출하는 **Repository 패턴** 적용.
  - **오프라인 폴백**: 통신 장애를 대비해 브라우저 `localStorage`를 이중 캐시로 사용.

## 1. 📂 아키텍처 및 폴더 구조 엄수 (Architecture Strictness)
프론트엔드와 백엔드의 역할과 위치를 엄격하게 분리하여 중복 코드를 방지합니다.

- **프론트엔드 (UI Layer)**: `src/front/` 내부에만 위치 (UI 렌더링, 뷰 컴포넌트)
- **백엔드 (Data Layer)**: `src/backend/` 내부에만 위치 (Supabase 통신, 서비스 로직, Repository)
- **금지 사항**: 과거 사용되던 `src/components/`나 `src/lib/services/` 등 동일한 기능의 폴더를 절대 중복 생성하거나 참조하지 않습니다.

## 2. ✂️ 단일 파일 크기 제한 (Max File Length 500 Lines)
가독성(Readability) 확보를 위해 하나의 코드 파일은 가급적 **500줄(Lines)**을 넘지 않도록 작성합니다.

- 코드가 길어질 경우, 의미 있는 단위(하위 컴포넌트, 커스텀 훅 등)로 반드시 분리(Refactoring)합니다.
- 거대 파일(God Object)이 감지되면 기능 구현보다 하위 모듈 분할을 우선시합니다.

## 3. 💬 명확한 한글 주석 의무화 (Mandatory Korean Comments)
유지 보수를 극대화하기 위해 코드의 기능과 목적에 따라 **한글 주석**을 반드시 달아야 합니다.

- **파일 최상단**: 해당 파일의 역할과 아키텍처 상의 위치를 설명하는 주석 필수.
- **함수 및 주요 로직**: 무엇을(What) 왜(Why) 하는지 명확한 한글 주석을 작성합니다.

## 4. 🧹 찌꺼기 코드 식별 및 삭제 원칙 (Zero Dead Code)
- 시스템에 중복되거나 작동하지 않는 레거시(Legacy) 코드나 파일이 발견되면 방치하지 않습니다.
- **원칙**: 반드시 사전 QA 및 컴파일/의존성 검증을 거친 후, 기능 상실이 확인되면 과감하게 삭제(Delete)합니다.

## 5. 🔗 Supabase 데이터 관계 및 참조 규칙 (Data Relationships)
Supabase의 테이블은 엄격한 정규화를 따릅니다. 프론트엔드나 컴포넌트에서 데이터를 화면에 뿌려줄 때는 다음을 주의하세요.
- `consultations` 테이블에는 차량번호(`car_number`)나 연락처(`phone_number`) 컬럼이 **존재하지 않습니다.**
- 반드시 `customer_id`를 키로 하여 `customers` 테이블/객체를 참조(`customers.find(...)`)하여 차량번호와 연락처 정보를 표시해야 합니다. (Admin 패널 및 칸반/캘린더 렌더링 시 누락되지 않도록 주의)

## 5.1 ⚙️ status - sub_status 무결성 자동 동기화 규칙 (Strict Status Alignment)
- **리포지토리 가드 원칙**: 상담 데이터를 저장(`saveConsultation`)하거나 읽어올 때, 대분류 `status` 컬럼은 반드시 `sub_status`(세부 프로세스 단계) 기준의 실효 상태(`getResolvedStatus`)로 100% 무조건 자동 연동(Synchronized)되어 저장 및 로드되어야 합니다.
- **불일치 방지**: `sub_status`가 '결제완료'/'처리완료'일 때 `status`가 '유선 부서 확인 중' 등 구 텍스트로 불일치하게 방치되는 현상을 리포지토리 레이어 차원에서 엄격히 차단합니다.

## 5.2 🚨 Supabase DB 저장 3대 철칙 (2026-08-20 확립, 절대 준수)
아래 규칙 위반 시 저장 오류 및 데이터 유실이 발생합니다. 에이전트는 저장 로직 수정 시 반드시 이 3가지를 점검해야 합니다.

**① customers 테이블: 고정 문자열 placeholder 절대 사용 금지**
- `customers.phone_number`와 `customers.car_number`는 **UNIQUE + NOT NULL** 제약이 있음
- `'미입력'`, `'미등록'` 등 고정 문자열 사용 시 두 번째 저장부터 `23505` 오류 발생
- **올바른 패턴**: phone/car 둘 다 없으면 Supabase 저장 건너뜀. 하나만 없으면 `no-phone-{uuid8}` 사용

**② consultations 테이블: customer_id FK 검증 필수**
- `consultations.customer_id`는 `customers.id`를 참조하는 FK (NULL 허용)
- Supabase에 존재하지 않는 UUID를 `customer_id`로 넣으면 `23503` 오류 발생
- **올바른 패턴**: 식별자(phone/car)가 없으면 `finalCustomerId = null` 사용. `saveCustomer()` 반환값의 ID를 반드시 사용

**③ upsert payload: DB에 없는 컬럼 포함 절대 금지**
- `consultations` 테이블에 없는 컬럼: `agent_id`, `car_number`, `phone_number`, `is_archived`
- 이 컬럼을 payload에 포함 시 PostgREST `400/409` 오류 발생
- **확인 방법**: `DEVELOPMENT_GUIDE.md > 3.2 ③` 허용 컬럼 목록 참조

## 6. 🛡️ Supabase 리소스 및 보안 규칙 (Resource & Security Rules)
무료 플랜의 한계(용량 및 트래픽)를 고려하여 데이터베이스 부하를 최소화해야 합니다.
1. **음성 파일(Audio) 저장 금지**: CTI 서버의 오디오 파일(.wav, .mp3)을 Supabase Storage나 DB에 직접 저장하지 마세요. 기존 녹취 서버의 URL 주소(`audio_url`) 문자열만 저장하여 스트리밍 방식으로 구현합니다.
2. **STT 텍스트와 요약본 분리**: 용량이 큰 STT 전체 원문(`stt_script`)과 2~3줄의 핵심 요약본(`ai_summary`)을 분리하여 설계하세요. 원문은 필요할 때만 비동기 로드하거나 일정 기간 후 삭제하여 DB 무게를 줄입니다.
3. **RLS (Row Level Security) 필수**: 사내 인증을 거치지 않은 외부인이 API Key를 탈취하여 트래픽(Egress)을 고갈시키지 않도록 반드시 행 단위 보안 정책(RLS)을 적용해야 합니다. (2026-08-11 기준 7개 모든 테이블에 `authenticated` 세션 전용 ALL 허용 RLS 가동 완료)
4. **외래키 Cascade 삭제 주의 (무결성 보존)**: 담당 상담원이 퇴사/계정 삭제되더라도, 기존 상담 이력은 보존되어야 합니다. 상담원 정보 참조 시 `ON DELETE CASCADE`를 차단하고, 삭제된 상담원임을 표시하는 방식을 사용하세요.

## 7. 📝 작업 세션 마무리 및 다음 에이전트 인수인계 규칙 (Handover & Wrap-up Protocol)

사용자가 **"오늘 작업 마무리해줘"**, **"오늘은 여기까지 하자"**, **"정리하자"**, **"마무리하자"** 등의 세션 종료 및 정리 지시를 내리면, 작업자 및 AI 에이전트는 즉시 작업을 수행하지 말고 **반드시 승인 요청(1단계)을 먼저 진행**해야 합니다.

### [1단계] 승인 요청 (사용자 의사 확인)
> 💬 **필수 시작 멘트**:
> **"오늘 하루 고생하셨습니다! 방금 작업한 내용들과 앞으로의 작업 내용을 정리해서 마무리할까요??"**

### [2단계] 마무리 필수 절차 4단계 실행
사용자로부터 **"어 그렇게 하자"**, **"응 승인"**, **"좋아"** 등의 확답을 받은 직후에만 아래 4단계 인수인계 절차를 이행합니다:

1. **빌드 & QA 검수**: `npx tsc --noEmit`을 실행하여 컴파일 오류가 0건임을 확인하고, 임시 디버그 주석이나 미사용 찌꺼기 코드/파일을 완전히 정돈합니다.
2. **개발 가이드 최신화 (`DEVELOPMENT_GUIDE.md`)**:
   - 오늘 작업에서 새로 적용된 컴포넌트 구조, 데이터 바인딩 로직, 상태 락(Ref Lock) 패턴, RLS/보안 정책을 규격화하여 명시합니다.
3. **프로젝트 로드맵 최신화 (`PROJECT_ROADMAP.md`)**:
   - **섹션 3 (완료된 작업)**: 오늘 날짜와 함께 새로 구현 완료된 기능 세부 항목을 추가합니다.
   - **섹션 4 (다음 단계 과제)**: 다음 에이전트가 오자마자 무엇부터 개발해야 하는지 우선순위별(Phase 1.5, Phase 2.0 등) 상세 기획 및 구현 가이드를 명확히 기록합니다.
   - **섹션 5 (핵심 파일 위치)**: 새로 추가되거나 변경된 핵심 파일 및 커스텀 훅(`useNotifications.ts`, `ProcessStepper.tsx` 등)의 위치와 역할을 표에 업데이트합니다.
4. **사용자 브리핑 & 다음 에이전트 지시문 제시**:
   - 오늘 완수된 기능 요약과 함께, **"다음 에이전트에게 전달할 프롬프트 메시지 예시"**를 템플릿 형태로 작성하여 사용자에게 안내합니다.

## 8. 🖼️ UI/UX 일관성 원칙 (UI/UX Consistency Rules)
- **모달(Modal) 백드롭 디스미스(Backdrop Dismiss) 제어**: 모든 모달 컴포넌트는 반드시 "외부 딤(Dim) 영역 클릭 시 닫히는 기능"을 포함해야 합니다.
  - 최상위 오버레이(백드롭) `div`에 `onClick={onClose}` 이벤트를 바인딩하여 외부 클릭 해제를 지원합니다.
  - 모달 컨텐츠 내부 `div`에는 이벤트 버블링을 막기 위해 `onClick={(e) => e.stopPropagation()}`을 반드시 추가하여 의도치 않은 닫힘을 방지합니다.
  - 향후 신규 모달 개발 시에도 이 원칙(Click-away to close)을 무조건 적용하여 사용자 경험(UX)의 일관성을 유지해야 합니다.

## 9. 🛡️ 부작용 방지 및 사용자 승인 의무 규칙 (Regression Prevention & User Permission Guard)
- **기존 기능 파괴 완전 차단 (No Side-Effects)**: 작업자 및 AI 에이전트는 신규 기능을 개발하거나 기존 코드를 수정할 때, **기존에 잘 작동하던 다른 기능(상담 저장, 검색, 매칭, 캘린더 연동 등)에 단 1%의 부정적 영향이나 오작동을 유발하지 않도록** 보수적으로 검증해야 합니다.
- **사전 승인 의무화 (Ask Before Change)**: 코드를 변경하는 과정에서 타 기능의 연동성이나 기존 동작 방식에 조금이라도 영향을 줄 수 있는 기획/개발적 선택(대체 기준 지정, 기본값 변경 등)이 필요할 경우, **독단적으로 결정하지 말고 반드시 사용자에게 현상을 설명하고 명시적 승인을 얻은 후에 진행**해야 합니다.
